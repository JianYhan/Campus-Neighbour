# Campus Neighbour 团队阅读版

版本：v0.2，2026年9月18日。适合全体成员阅读，不需要编程基础。

## 我们到底要做什么

做一个校园二手交易网站，让同学更方便地找闲置物品、沟通和约见面交。我们重点解决三个问题：信息散落在不同群聊、看不清商品是否已被预约或售出、很难按楼栋或课程找到合适物品。

例如：小林想买高数教材，选择自己的课程和附近楼栋，找到小陈发布的书。他们在网站上聊天，约好面交。小林拿到书后点击确认收货，交易完成，双方可以评价。

网站支持电脑和手机浏览器；界面可以切换中文和英文，也可以切换浅色和深色主题。用户自己写的商品介绍和聊天消息保留原文，首版不承诺自动翻译。

## 为什么需要需求文档

需求文档是大家对“系统应该怎样工作”的共同约定。它帮助设计页面、分配任务、编写程序和判断是否完成。

比如“支持预约”这四个字不够明确：谁发起预约？能否同时预约给两个人？取消后还能不能买？如果不提前说清楚，页面设计和程序实现就可能不一致。

需求文档也方便检查成果。不能只看有没有“确认收货”按钮，还要检查：是不是只有买家能点，点完后商品会不会变成已售出，重复点会不会出错。

它会随着讨论和测试修订，不代表所有建议都已经定案。申报书负责说明项目方向；需求文档负责把方向落实成可执行的规则；后续技术文档解释程序如何实现这些规则。

## 第一阶段要能完成什么

1. 注册、登录，填写基础资料。
2. 卖家发布商品，上传图片，填写价格、成色和地点。
3. 买家搜索商品，按价格、楼栋和课程筛选。
4. 买卖双方通过商品关联的实时聊天沟通，使用问价格、问状态、问地点按钮，或选择20字以内自由消息。
5. 为指定买家保留商品，记录面交安排。
6. 买家拿到物品后确认收货，完成交易并评价。
7. 显示新消息和交易变化，管理员能处理违规内容。
8. 展示支付入口；点击后提示暂时无法提供支付方式，不收取资金。

这些功能要连起来使用。例如：只有商品发布页和聊天页，却不能完成一次交易，还不算这一阶段完成。

## 后续在同一平台里完善什么

- 买卖双方的学院、专业、年级简介。
- 教材关联课程、版本、任课老师和简要课程介绍。
- 毕业季、开学季商品专区。
- 一对一以物换物：双方同意交换，各自收到物品后确认。

关于核心聊天功能：例如，小林点击“问交易地点”，确认后这句话会发给小陈，由小陈回复。选择“自由聊天”则可以自己写消息；双方都能回复，单条自由消息暂按20字上限，可以连续发多条。这些都是人与人聊天，不是AI自动问答。完整英文快捷模板如何处理长度，详细版中已列为待确认规则。

聊天快捷入口随核心聊天功能实现。地图、美食、生活指南等保留为未来扩展，当前申报范围不自动扩大。

## 几条所有人都应该理解的规则

- 一件商品同一时间只能被一笔有效交易占用，不能承诺给两个买家。
- 普通买卖由买家确认收货；卖家不能代替买家确认。
- 只有完成交易的参与者能评价。
- 私聊只有会话双方可以看。
- 取消预约后，仍允许展示的商品才恢复可交易。
- 支付展示页不会产生真实付款，也不会让订单自动完成。
- 换物要双方都确认收到物品才算完成。

预约如何发起、什么情况下可以取消、评分采用几分制等细节仍待讨论。详细版中写“建议”的地方，就是可以一起讨论的地方。

## 不同成员怎样使用这些文档

| 工作 | 阅读重点 | 可以交付的成果 |
| --- | --- | --- |
| 页面和体验设计 | 使用流程、页面、提示和错误情况 | 原型、页面说明、中文英文文案 |
| 程序开发 | 功能规则、权限、数据和接口 | 能运行的功能、相关测试 |
| 测试和用户试用 | 每项功能怎样算完成 | 操作步骤、预期结果、问题截图、复测记录 |
| 文档和展示 | 项目目标、已实现功能、真实测试结果 | 使用说明、报告素材、演示脚本 |
| 项目协调 | 功能范围、依赖和截止日期 | 任务记录、会议结论、进度更新 |

每个人先读这份简明版，再重点阅读自己负责部分的详细需求。不需要所有成员立即掌握所有技术术语。

## 详细版里的缩写是什么意思

- SRS：软件需求规格说明书，就是完整的系统行为约定。
- FR：功能编号，方便告诉别人“我们在讨论哪一项功能”。
- NFR：质量要求，例如安全、速度、易用性。
- AT：验收场景，说明如何实际检查功能。
- P0：先完成的核心功能；P1：后续迭代仍计划交付的功能。
- D：还需要讨论和确认的决定。

简明版帮助理解；开发和验收以最新详细版及记录下来的修改决定为准。如果两份文档内容不一致，需要同步修改，不让团队保留两套相互矛盾的规则。

## 现在可以怎样参与评审

8份工程文档初稿已经齐备，入口在[仓库首页](../README.md)。先看[页面设计](product-design.md)，想象自己实际发布、聊天和交易；记录哪一步不清楚，再核对详细需求。不需要先读懂所有数据库字段才能提出意见。

开发方式已确定为TDD（测试驱动开发）：例如先写“第三人不能查看私聊”的测试，确认当前缺少保护时测试失败，再实现权限检查让它通过，最后整理代码。每个功能持续这样小步推进，不能等整个系统写完才补测试。具体流程见[协作规范](../CONTRIBUTING.md)。
