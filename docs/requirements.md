## 1 文档定位与项目范围

Campus Neighbour 是面向校园学生的二手交易平台，解决信息分散、交易状态不透明、缺少校园专属检索三个问题。通过楼栋、课程和教材信息帮助用户发现商品，使用站内聊天和线下面交完成交易，促进物品重复利用。

申报书确定的主流程为：卖家发布商品 → 买家浏览或搜索 → 双方站内沟通 → 预约线下面交 → 买家确认收货 → 完成交易并评价。平台不处理真实资金。

本文使用以下标记：

- **确定范围**：申报书已包含的功能，不因本文提出实现建议而改变。
- **建议规则**：为使需求可执行而补充的默认方案，需团队评审确认；不是已经获得团队批准的决定。
- **待定项 Dxx**：尚缺信息的决策，见第9节。相关实现开始前应完成确认。

交付分级不是删除功能：P0为首先跑通的核心流程；P1为本项目后续迭代功能。P1仍属于计划交付范围。

- P0：账号、基础资料、商品管理、搜索筛选、私聊、预约与取消、收货确认、评价、基础管理、站内通知、支付展示页。
- P1：完整校园及课程简介、季节专区、一对一以物换物。
- P0聊天细化：实时聊天窗口提供三个快捷询问按钮及20字以内自由消息入口，消息发给交易对方并由对方回复。此项不使用AI自动回答。
- Future Work：地图、美食和生活指南、选修课评价、复杂推荐、多方换物、配送、真实支付与担保、商家自助管理。

不预设学校统一身份认证、官方教务数据或校内地图接口已经可用。未经评审不增加新的业务模块。技术框架、版本和服务商由独立的技术选型文档确定。

## 2 用户角色与典型场景

角色建议如下，访客访问范围和注册方式见D01。

- 访客：浏览公开商品和公开简介；进行交易相关操作前登录。
- 学生：同一账号可同时作为买家和卖家，管理自己的商品、会话、交易和资料。
- 管理员：管理基础分类与校园字典、处理违规商品、限制违规账号，并记录处理理由。管理员权限不得由普通注册者自行选择。

典型场景：

- UC01 同楼交易：学生按楼栋和价格筛选商品，联系卖家，下楼面交后确认收货。
- UC02 按课找书：学生按课程及教材版本筛选，参考卖家的专业、年级和课程背景，确认教材是否适用。
- UC03 交易状态查询：学生能区分可交易、已预约、已售出，避免对已成交商品重复发起预约。
- UC04 毕业季处理闲置：卖家正常发布商品，符合专区条件的商品被集中展示，商品状态在专区同步更新。
- UC05 换物：两个学生选择各自一件商品，在双方接受后进行线下交换并分别确认收到物品。
- UC06 快捷聊天：买家在与卖家的实时聊天窗口点击价格、状态或地点按钮，发送对应问题；也可选择自由聊天，输入不超过20字的消息。卖家在同一会话回复，买家可继续交流。

私人会话和交易详情仅向参与者开放。公开个人资料不展示登录凭据、学号、联系方式、具体宿舍房间号；身份验证信息与公开简介分离。是否允许额外公开联系信息见D02。

## 3 核心功能需求

每条需求编号在页面设计、接口和测试中继续引用，以便检查遗漏。

### FR01 账号与个人资料 P0

系统应提供注册、登录、退出及个人资料编辑；密码等凭据不得明文保存。注册是否验证校园邮箱见D01，不得把未验证用户标记为学校认证用户。用户只能编辑自己的资料。

验收：两个测试账号可以独立登录；退出后受保护操作要求重新登录；修改请求中的用户编号不能编辑他人资料。

### FR02 商品发布与管理 P0

卖家应能发布、编辑和下架自己的商品。信息包含标题、照片、描述、成色、价格、分类和校园地点；教材可填写课程、作者、版本。必填项、图片数量及大小见D03。价格不得为负，金额显示及校验保持一致。

建议规则：预约前可修改交易关键信息；预约后价格和物品信息保留交易快照，变更约定需先取消再重新预约。删除或下架不应破坏既有会话、交易和评价记录。

验收：缺少必填项时给出具体提示；非所有者修改被拒绝；已预约商品的原有交易资料可回查。

### FR03 浏览搜索与筛选 P0

系统应支持关键词搜索，并按分类、价格区间、楼栋和课程组合筛选。支持分页或等效分批加载；无结果时提供调整条件入口。教材版本应在详情中清楚展示。

验收：准备有明确预期结果的商品数据，组合筛选返回满足全部条件的结果；非法价格范围提示修正；不可见商品不得通过搜索或直接链接泄露。

### FR04 站内私聊 P0

买家应能从商品详情联系卖家；会话应保留商品关联、发送人和时间。仅会话参与者可读写。聊天窗口提供快捷问题及自由聊天选项；自由输入的单条消息暂按20字上限，双方可连续发送多条消息。该限制属于买卖双方聊天，不存在独立AI聊天入口。附件支持见D04，首版建议仅支持文字。

验收：双方能收发和重新打开历史消息；第三人无法读取；发送失败可见且可重试，不将失败显示为成功。

### FR05 预约与线下面交 P0

建议由卖家在与指定买家的会话中创建预约，记录约定地点和时间，买家可查看；这体现申报书中的“卖家为一个买家保留商品”。确认方式及取消规则见D05。公开的建议交易地点和双方约定的具体面交信息应分开保存。

验收：同一商品同时尝试为两个买家预约，只能有一个成功；重复点击不产生重复有效交易；面交信息只向双方开放。

### FR06 收货确认与完成 P0

普通买卖仅由该交易买家执行确认收货，界面应在提交前提示其含义。成功后交易完成，商品标记已售出，并开放评价。该动作不表示平台确认付款成功。

验收：卖家或第三人无法冒充买家确认；取消交易无法确认；重复确认只返回同一完成结果，不重复触发业务动作。

### FR07 交易评价 P0

完成交易的双方应能评价对方。建议每人对每笔交易评价一次，包含评分和文字；评分尺度、是否可修改及展示位置见D06。首版不建立未经确定的信用分惩罚算法。

验收：未完成交易及非参与者不能评价；重复提交不形成多条评价；评价关联真实的平台交易记录。

### FR08 管理与通知 P0

管理员应能查看和下架违规商品、限制违规账号，记录操作者、时间和理由。通知至少覆盖新消息提示、预约、取消和交易完成；具体采用站内通知，无需短信或邮件服务。普通用户不能调用管理操作。

验收：被下架商品不再出现在公开列表；已有交易仍能查看必要记录；越权请求被拒绝；通知跳转仍执行访问权限检查。账号受限后的存量交易处理见D07。

### FR09 支付展示页 P0

点击Pay应进入展示页面，明确显示“暂时无法提供支付方式”，并允许返回。平台不采集支付凭据，不接入支付服务、不转账、不记录支付成功。建议设置独立的可演示入口，不能成为完成线下面交的必经阻塞步骤。

验收：进入、刷新、返回该页均不改变交易状态，不出现“支付成功”反馈，也不产生资金流水。

## 4 校园特色与换物需求

### FR10 校园及课程简介 P1

买卖双方可填写学院、专业、年级和个人简介；课程背景可包含课程名、任课老师和课程简述。建议这些背景字段为选填，并在商品详情提供卖家简介入口。任课老师和课程介绍均是用户填写资料，不应暗示得到学校官方认可。

验收：未填选填项仍可正常交易；资料修改正确展示；公开页不泄露用于登录或身份验证的内部字段。

### FR11 校园字典与季节专区 P1

楼栋、课程、分类使用统一选项，避免同一名称多种写法影响检索。季节专区复用正常商品；建议管理员配置开始与结束时间、纳入条件，不复制商品记录。初始字典和专区规则见D08。

验收：同一商品在专区和详情状态一致；已售出或下架后不再显示为可交易；专区启停按所选时区生效。

### FR12 一对一以物换物 P1

用户应能标记愿意换物并描述希望换得的物品，通过现有列表寻找对象，为“一件自己的商品换一件对方商品”发起请求。系统展示双方物品，只有双方明确接受后才建立有效换物预约。首版不承诺智能匹配、多方交换或补差价。

建议规则：请求尚未被接受时不锁定商品；接受时同时检查并锁定两件商品，任何一件不可用则整次接受失败。创建请求视为发起方表达接受；对方接受前任何商品发生实质变化，应要求重新确认。该规则待D09评审。

换物双方分别确认收到对方物品，双方均确认后整笔交易完成，两件商品标记已交换，并开放评价。单方确认后显示“等待另一方确认”。存在交付分歧时保留记录，不自动认定另一方已经收到物品。

验收：不能用他人的物品发起换物；不能交换自己的两件物品；两个同时接受请求不能重复占用同一商品；单方确认不会提前完成整笔交易。

## 5 实时聊天中的快捷询问与自由消息

本节是FR04站内私聊的交互细化。消息由用户发送给会话对方，由对方人工回复；系统不读取商品资料生成自动回答，也不调用模型API。

### FR13 三个快捷询问按钮 P0

在商品关联的买卖双方实时聊天窗口提供“问价格”“问物品状态”“问交易地点”。建议点击后将对应问题放入输入框，由用户确认发送。例如：“请问价格是多少？”“请问物品现在是什么状态？”“请问在哪里交易？”按钮文案随界面语言切换。

快捷问题作为真实用户消息保存到当前会话，与普通文字消息使用相同的权限、通知和历史记录机制。发送问题本身不会修改价格、商品状态或面交安排。

验收：三个按钮发送正确的问题给当前会话对方，不产生机器人回复；其他用户不能读取；切换中英文后模板与界面语言一致。

### FR14 20字以内自由聊天 P0

用户选择“自由聊天”后可自行输入文字并发给对方；买家和卖家均可使用。当前单条自由消息上限暂定20个用户可见字符，包含标点、空格与表情；允许连续发送多条，空白输入不可提交。前后端使用同一计数定义，以服务端校验为准。

固定快捷模板作为独立消息类型，由服务端根据模板编号和发送语言生成；不受自由输入20字上限限制，以支持完整英文句子。模板编辑后按自由消息校验。该模板规则为建议，待D10确认，不是更改自由消息上限。

验收：空白和21字自由消息不能发送；20字可发送；双方可以在同一会话回复；固定模板例外不能被用来绕过任意长文本校验。具体英文输入体验见D04。

### FR15 发送反馈与历史一致性 P0

快捷问题与自由消息均展示发送中、发送成功或失败状态；失败可重试。重新进入会话后可查看已保存的消息，重连补取遗漏记录，重复请求不产生多条同一消息。快捷发送不得绕过登录及会话参与者校验。

验收：断线和重试不会显示虚假发送成功；历史记录保留实际发送文字，不因用户后来切换界面语言而被改写；对方回复按照真实发送人显示。

## 6 交易状态与业务约束

以下状态设计是建议基线，评审后成为实现和测试共同依据；字段名称可以在接口设计中统一。

商品状态：可交易、已预约、已售出、已交换、已下架。交易状态与商品状态分开保存，不能用一个字段同时表示两者。

- 发布成功 → 商品可交易。
- 普通买卖预约成功 → 交易待面交，商品已预约。
- 买家确认收货 → 交易已完成，商品已售出。
- 面交前取消 → 交易已取消；商品仅在仍符合展示条件时恢复可交易，否则保持已下架。
- 换物双方接受 → 换物待面交，两件商品已预约。
- 一方确认 → 等待另一方确认，两件商品仍被本交易占用。
- 双方确认 → 换物已完成，两件商品已交换。
- 管理下架 → 停止公开展示；不得抹除既有交易记录或自动伪造交易完成。

约束：

- 同一商品同一时刻最多属于一笔有效预约，包括买卖和换物。
- 预约创建、取消和完成必须作为不可分割的操作更新关联记录，不能出现订单完成而商品仍可被购买的状态。
- 重复请求不产生重复预约、评价或确认记录。
- 只有交易参与者可以执行其角色允许的操作；管理员也不能代买家假装收货。
- 建议双方在未确认交付前均可取消并填写原因；换物一方已确认后不能直接释放两件商品。异常关闭流程见D05、D09。
- 完成后不支持自动回退、退款或平台担保；争议处理不承诺资金追偿。

## 7 数据与页面边界

本节描述必须保留的信息，不指定数据库表或具体URL。详细字段与接口由后续设计文档定义。

主要数据对象：账号与权限、公开简介、楼栋与课程字典、商品及图片、会话与消息、买卖交易、换物请求与交易、评价、通知、专区配置、管理操作记录。

交易应保存参与者、关联商品、约定信息、商品关键资料快照、状态及关键动作时间。聊天与交易历史不得因商品后续修改而产生无法解释的变化。账号删除、记录保留期限和测试结束后的数据清理见D11。

页面清单：

- P01 登录与注册；P02 首页／商品列表及筛选；P03 商品详情、卖家简介和联系卖家入口。
- P04 发布／编辑商品；P05 我的商品；P06 会话列表及聊天，包含快捷询问和自由消息。
- P07 我的交易；P08 交易详情、预约信息、确认和评价；P09 支付展示页。
- P10 个人资料及他人公开简介；P11 季节专区；P12 换物请求及确认。
- P13 管理后台；通知可作为公共导航入口，不要求独立页面。

每页原型需要覆盖正常、加载、空数据、错误、未登录和无权限状态。移动端应能完成主要交易操作，不能只做桌面截图。

外部依赖：校园身份服务尚未确认；图片存储和部署环境需按技术方案落实；本次聊天不依赖外部AI服务。以上依赖必须具备本地开发或演示替代方案，不影响核心交易的验收。

## 8 质量要求与验收方法

- NFR01 安全与隔离：登录和角色检查由服务端执行；对会话、商品修改及交易操作逐项验证资源归属。拒绝伪造身份和跨账号访问。
- NFR02 输入与文件安全：服务端校验字段、图片类型与大小；用户文本按文本展示，不执行脚本；错误反馈不暴露凭据或内部堆栈。
- NFR03 一致性与恢复：并发预约不会重复占用；刷新或重试不重复执行；连接中断后可以重新查询真实状态，不能把未知结果当作成功。
- NFR04 易用性：关键操作有明确反馈；状态不只靠颜色表达；表单标签和错误信息可理解；按钮支持键盘操作，移动端无阻碍主要流程的横向溢出。
- NFR07 主题与语言：所有主要页面支持浅色／深色主题和中文／英文界面切换，保存选择；翻译覆盖按钮、提示、错误及快捷问题模板。商品描述和聊天历史保留原文。验收覆盖两种主题与两种语言，切换不丢失当前交易或已输入消息。
- NFR05 性能：在约定的演示环境、数据规模与并发量下测试列表、消息和预约响应。目标值待D12确定；记录真实测量值，不先承诺未经验证的指标。
- NFR06 可维护与复现：新成员按运行说明可启动项目和测试数据；配置与密钥分离；接口、数据库变更与文档同步更新；不使用真实学生隐私作为公开演示数据。

最低验收场景与追踪：
