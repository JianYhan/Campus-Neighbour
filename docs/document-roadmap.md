# Campus Neighbour 文档与开发路线

日期：2026年9月18日。本文是团队工作建议，不新增课程提交要求。已完成的申报书继续作为项目范围依据。

## 文档数量与职责

建议维护8份工程文档：当前已起草第1份，后续还有7份。每份可以是仓库中的一个Markdown文件或一个目录，不要求全部做成长篇Word。

1. **软件需求规格说明书 SRS**：做什么、角色权限、业务规则、范围、验收标准；当前v0.1是讨论稿。建议路径 docs/requirements.md。
2. **功能与页面设计**：合并详细功能设计、用例、流程图、交易状态图和页面原型。逐页写输入、按钮、跳转、正常及异常状态，引用需求编号。建议路径 docs/product-design/。
3. **技术选型与系统架构**：框架和版本、选择理由、系统边界、模块划分、运行与部署方式、关键技术决策。建议路径 docs/architecture.md。
4. **数据库设计**：实体关系图、数据字典、约束、索引、状态及快照存储、迁移和初始数据。建议路径 docs/database.md。
5. **接口契约**：路由、方法、鉴权、请求响应、错误码、分页、时间金额格式、重复请求处理、消息事件。优先维护可校验的OpenAPI文件，示例使用虚构数据。建议路径 docs/api/。
6. **开发协作与任务计划**：目录约定、命名、代码检查、分支和合并规则、环境配置、任务依赖、负责人和完成标准。任务状态尽量用GitHub Issues维护，文档避免重复记账。建议路径 CONTRIBUTING.md及任务看板。
7. **测试计划与验收记录**：需求对应测试、测试数据、权限与并发场景、快捷聊天验证、缺陷、复测及证据。先写计划，开发过程中持续填写结果。建议路径 docs/testing/。
8. **部署运行与用户说明**：分别面向开发者和用户，包含环境、启动、配置、演示账号、常见问题、操作步骤、备份与恢复；可在同一目录分成两篇短文。建议路径 docs/operations/和docs/user-guide/。

另有课程交付材料：技术报告、展示材料、Project Updates。它们是交付类别，不算额外的三份工程设计文档；技术报告引用并整理上述材料，用户说明按课程模板独立导出。报告篇幅和格式以课程原文件为准。

## 技术栈需要约定什么

不能只决定“用Vue还是React”。选型至少需要记录：

- 团队实际熟悉的语言、可投入人员和开发环境。
- 前端框架、语言、构建工具、路由、组件库、表单与状态管理。
- 后端语言、框架、运行时版本、依赖管理和模块结构。
- 数据库、访问方式、迁移工具、演示数据准备方式。
- 登录会话方案、权限校验、跨域与凭据配置。
- 聊天和通知的更新机制；是否需要持久连接，以体验和实现成本决定。
- 图片存储、上传限制与开发环境替代方案。
- 快捷聊天模板、自由消息20字校验、中英切换及发送失败处理。
- 测试、格式检查、代码审查、持续集成和发布步骤。
- 部署机器或平台、环境变量、日志、备份、域名及预算。

前端已选择React、TypeScript、Tailwind和pnpm；后端方案见技术选型评审。具体依赖版本仍需用登录、商品列表、数据库写入及一次消息更新的小样验证后锁定。最新兼容性和部署限制应在正式选型时依据官方文档核对。

建议架构起点是一个前端、一个模块化后端、一个关系数据库，按账号、商品、聊天、交易等划分模块。快捷询问和自由消息归属聊天模块，不设置AI问答模块。选型必须解释为什么需要额外组件，不因功能数量多就直接增加独立服务。

## 开始开发的顺序

第一步：评审SRS范围、角色和交易规则，同时了解团队技术经验。

第二步：画核心交易页面及状态图，并完成技术选型。原型用来发现业务遗漏，技术小样用来验证实现风险。

第三步：确定账号、商品及交易的基础数据结构和接口规则；写核心验收用例、协作规范和任务依赖。

第四步：先实现一个能运行的短流程：登录、发布、列表、详情，再接聊天、预约、收货和评价。每个模块开始前细化它的接口和验收条件。

第五步：继续校园功能、换物和完善后的实时聊天，边实现边更新文档与测试。最后完成运行说明、用户说明和课程材料。

开工条件不是八份文档全部定稿，而是当前开发模块的需求、页面、技术、数据、接口和验收条件相互一致。第一次整合应尽早进行，不能等每个人各自完成整个模块后再连接。
